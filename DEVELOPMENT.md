# CyberKiwi Client Development Guide

## Project Overview

**CyberKiwi Client** is the cross-platform frontend for CyberKiwi - a cybersecurity news intelligence platform. Built with React 19 + TypeScript + Vite + Capacitor + Electron + Tauri.

- **Bundle ID / Package**: `com.cyberkiwi.client`
- **App Name**: `CyberKiwi`
- **Version**: `1.0.0`
- **Min iOS**: `16.0`
- **Min Android SDK**: `24`

---

## Prerequisites

- macOS with Xcode 15+ (for iOS)
- Node.js 20.x
- Apple Developer Account ($99/yr) for TestFlight/App Store
- Android Studio (for Android)
- CocoaPods (`sudo gem install cocoapods`)

## Environment Variables

Create `.env` from `.env.example`:
```bash
VITE_APP_VERSION=1.0.0
GEMINI_API_KEY=your_server_side_key  # Only used by server.ts
NVD_API_KEY=your_nvd_key  # Optional. Only used by the ingestion worker's NVD adapter
ALLOWED_ORIGIN=https://cyberkiwi.app  # Production CORS
```

Local overrides go in `.env.local` (git-ignored). The ingestion scripts (`worker:once`, `worker:ingest`, `catalog:check`) load `.env` first, then `.env.local`, which overrides it. Real process environment variables (for example CI secrets) take priority over both files.

## Database and ingestion worker (Phase 1)

PostgreSQL runs in Docker on host port **5433** (container port 5432), so it does not collide with other local databases.

```bash
npm run db:up          # start PostgreSQL (Docker Desktop must be running)
npm run db:deploy      # apply migrations to DATABASE_URL
npm run db:seed        # load the bundled feed catalog (idempotent)
npm run worker:once    # run one ingestion cycle
npm run worker:ingest  # run the worker continuously (WORKER_INTERVAL_MS)
npm run test:db        # PostgreSQL integration tests (uses cyberkiwi_test)
npm run db:down        # stop PostgreSQL
```

Default connection: `postgresql://cyberkiwi:cyberkiwi@localhost:5433/cyberkiwi`. Override with `DATABASE_URL`. Never point the integration tests at a database whose name does not end in `_test`.

`worker:ingest` runs one cycle immediately, then starts a non-overlapping scheduler. Set `WORKER_INTERVAL_MS` to change the scheduler interval and `WORKER_CONCURRENCY` to change the number of feeds processed in parallel. Each feed still uses its own interval and exponential backoff, so a failing source does not block healthy sources. Run `worker:ingest` as a separate supervised process from the API server in production.

Use `worker:once` for a manual refresh, a scheduled job, or a deployment check. The worker stores articles and stories in PostgreSQL. The browser reads those persisted records through `/api/v1`; browser refreshes never fetch publisher feeds directly when `VITE_CYBERKIWI_API_BASE_URL` is configured.

Ingestion rules are in [docs/ingestion-contract.md](docs/ingestion-contract.md). All feed fetching goes through `server/netSafety.ts`.

## CyberKiwi API base URL per target

The client reads its API origin from VITE_CYBERKIWI_API_BASE_URL at build time. Vite embeds the value in the bundle, so the URL is fixed for each build. Desktop, mobile and pre-beta builds therefore target different backends by building with different values. The URL is never hard-coded in the source.

| Target | Setting | Notes |
|---|---|---|
| Web (dev) | unset, or empty for same-origin | The dev server serves /api/v1 on the same origin |
| Electron, Tauri, Capacitor (Android, iOS) | required for release | Empty or unset means local feed fetching, not the CyberKiwi API |
| Pre-beta and production | required, https only | Set in the CI secret store for the release job |

Before a release build, run the guard. It fails when the URL is missing, not https, or contains a query or fragment:

    VITE_CYBERKIWI_API_BASE_URL=https://api.example.com npm run release:check-api
    npm run build

In PowerShell, set the variable with $env:VITE_CYBERKIWI_API_BASE_URL = "https://api.example.com" before running the same commands. Local development against a loopback server may use http with ALLOW_HTTP_API=1.

Android and iOS builds: Android uses cleartext only in development (capacitor.config.ts). Release builds must use https, so the packaged app can reach the API without exceptions. Run npm run build:android after the URL is set, then cap sync ios, so the native projects carry the new bundle.

## Source catalog maintenance

The bundled catalog is src/data/cybersecFeeds.ts. Decisions about it (disabled sources, adapters, size overrides) are code-owned in server/ingestion/catalogPolicy.ts. A feed listed there as disabled stays in the catalog with its reason, and the dashboard explains an empty block from source health, not from guesswork.

    npm run db:seed          apply the catalog decisions to the database (idempotent)
    npm run catalog:check    read-only report: HTTP status, parse result, items, last successful fetch
    npm run worker:once      one ingestion cycle

catalog:check exits 1 when an enabled source fails, so it can gate a catalog change. NVD is read through its CVE 2.0 API adapter. NVD answers 503 at times; those runs fail, back off, and resume from the same point. When `NVD_API_KEY` is set, the adapter sends it as an `apiKey` header. The key is read only on the server and is never logged. Pacing stays in place with or without a key. An invalid key makes NVD reject every request (`Invalid apiKey.`), so the source fails until the key is fixed.

Empty dashboard blocks say why they are empty: no matching stories, no active sources for the topic, or all sources for the topic failing.

The dashboard includes separate blocks for Cloud, IoT, AppSec, DevSecOps and Privacy. Saved pre-beta dashboards migrate the former combined Cloud and IoT block automatically. The current catalog has no active source for Cloud, AppSec, DevSecOps or Privacy, and the IoT source may display a temporary failure state until its next successful fetch. Add only verified replacement URLs in `src/data/cybersecFeeds.ts` and apply them with `npm run db:seed`.

### Responsive navigation and dialog accessibility

The navbar keeps topic links in a separate horizontal row so the brand, search field and actions do not overlap. At narrow widths, secondary actions move into the mobile menu. The reader and settings dialogs set an accessible dialog name, move focus into the dialog, trap `Tab` navigation, close on `Escape`, and restore focus to the opening control.
